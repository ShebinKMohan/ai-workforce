Agents Office 3.4.0-beta.1 is a business-assistant harness presented as a 3D office. It connects a department-based task interface to Claude, supplies agent personas with company notes and procedures, and saves generated deliverables. It is aimed at an owner handling email, sales, marketing, operations, finance and delivery work. It contains real model invocation code, but the office also simulates work and approvals while displaying LIVE. It is not evidence of an autonomous software engineering team.

Features and source map:
- Office UI: six departments and 35 fixed agent seats, task boards, agent chat, connector graphics and a searchable Brain graph. Department and seat definitions are in src/data.js:17–29; UI bundling is in build.mjs:1–24. Roster configuration can change names, roles, descriptions, usual tools and briefs, but cannot add seats or change department/lead membership (roster.mjs:17–49).
- Routing and deliverables: Claude selects one agent inside the user-selected department, with a department-lead fallback for an invalid choice. Another invocation creates the deliverable, normally limited by the prompt to 260 words unless instructions override it (serve.mjs:169–195). The generated plan is not an independently approved or executed workflow.
- Chat and revisions: persona chat includes selected notes, recent task titles and up to eight supplied history messages (serve.mjs:206–218). “revise: …” reruns the latest successful live deliverable and replaces the stored result (src/tasks.js:338–343; serve.mjs:255–275). Ordinary chat history is browser memory rather than a server-persisted transcript (src/main.js:805–832).
- Brain: Markdown company context and keyword-selected note excerpts enter prompts; this is lightweight text matching, not vector search (serve.mjs:128–157). The graph resolves wiki links, excludes isolated notes, and supports search, filters, navigation and relationship inspection rather than full-note reading (graph-build.mjs:15–58; src/brain.js:225–269).
- Instructions and learning: standing briefs and bound Markdown skills/templates enter prompts (skills.mjs:49–103). A department lead can conduct a five-question setup interview and write briefs plus a skill/template (onboard.mjs:16–108). Successful revision feedback is classified and stored as standing rules or one-offs; up to 15 recent rules enter later prompts. This is instruction memory, not model training (serve.mjs:272–275; learn.mjs:10–71).
- Connectors: the CLI discovers MCP servers and builds a global configured tool-prefix list, optionally including web search/fetch (mcp.mjs:66–108). Connector visuals and recorded tool names do not prove an external operation succeeded.
- Persistence: tasks are stored in data/tasks.json, while successful deliverables become Markdown under the configured Brain’s Agents Office folder (serve.mjs:71–75,197–204). Server task states are next, doing and done; caught failures also use done with error:true (serve.mjs:245–279).

A typical request proceeds as follows:
1. Select Sales and submit “Draft a proposal.” The browser posts department and text to /api/tasks (src/tasks.js:296–310).
2. The server asks Claude to choose one Sales agent and saves the routed task as next (serve.mjs:169–179,245–253).
3. The browser task loop starts /api/tasks/<id>/run when that agent reaches the task; execution depends on that browser scheduling path rather than an autonomous server queue (src/tasks.js:325–336,568–587).
4. The server reloads roster and skills, selects Brain excerpts and adds the persona, brief, lessons and tool instructions (serve.mjs:53–59,128–195).
5. A fresh Claude CLI process generates the answer, or the optional Anthropic SDK makes a messages request without configured tools (serve.mjs:63–114).
6. The server saves the result and note, rebuilds the graph, and returns the task. The browser displays the deliverable and updates connector/Brain visuals (serve.mjs:261–269; src/tasks.js:325–336). Progress is time-based animation capped at 92% while waiting, not measured model progress (src/tasks.js:575–578).

Important boundaries:
- LIVE does not remove demo behavior. Persisted tasks are appended to the existing board, idle agents can receive simulated tasks, random approvals continue, and “add task: …” in chat uses the local simulated path. Failed live intake also falls back to that path (src/tasks.js:312–315,345–375,544–587; src/main.js:817–820,1217–1225).
- Department connector wiring and an agent’s usual-tools list are not per-agent authorization boundaries. allowedTools() uses global server filtering and takes no agent argument (mcp.mjs:53–64,104–123). CLI arguments explicitly disallow named shell, file and delegation tools, but the application does not implement an operation-level approval gate. Visible approvals change browser state, not server-side MCP authorization (serve.mjs:88–95,229–295; src/main.js:925–950). The report appropriately leaves the installed CLI’s full permission behavior unverified; the configured prefixes must not be treated as proof of complete isolation.
- Concurrency and recovery are basic. There is no server duplicate-run guard, durable lease, cancellation endpoint or exactly-once mechanism; reloading requeues unfinished tasks and can duplicate an invocation (serve.mjs:255–279; src/tasks.js:355–362). The usual CLI timeout is 300 seconds; the SDK path does not use that wrapper timeout (serve.mjs:45,81–114).
- Revisions overwrite stored results, and same-day tasks with matching title slugs can overwrite the same note. Tool records retain names rather than full operation evidence (serve.mjs:98–103,197–204,263–269).
- This implementation provides no native repository workspace, source-editing, terminal/test/build, Git, developer-delegation or independent engineering-verification workflow. A connector could add capabilities, but that would depend on the connector.
- The HTTP handler has no application authentication/origin check and does not explicitly bind loopback; actual network reachability is untested (serve.mjs:229–296). Claude inference and connectors can involve external services despite local file storage.

Runtime and configuration: package.json:2–26 declares version 3.4.0-beta.1, Node 20+, d3-force, build/UI dependencies and optional Anthropic SDK. Default execution uses Claude Code CLI; an API key selects the SDK if available. Model availability, including the literal SDK fallback “claude-opus-5,” was not verified (serve.mjs:63–92). Configuration precedence is shipped config, local config, then supported environment overrides (config.mjs:15–27). Roster precedence is built-ins, shipped roster, Brain roster, then local roster (roster.mjs:52–63). Northgate Studio is supplied example business content, not adoption evidence (office.config.json:2; brain/10-Business/business-model.md:3–4).
