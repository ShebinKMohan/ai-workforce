07 / Recovery with historyInterrupted work should leave something useful behind.

When a run stops,
your context shouldn’t disappear.

Requests, attempts, errors and candidate artifacts stay recorded so the next action starts from what actually happened.

See the reason

Clear waiting and failure states

Distinguish available capacity, sign-in needs, rejected review, failed checks and stopped work.

Continue deliberately

Stop, resume and retry

Use the saved run settings and preserve earlier attempts. Known temporary provider failures have a finite retry budget.

Keep useful evidence

A history you can reopen

Read the original request, phase timing, assigned people, messages, results and recorded checks.

App-managed capacity covers concurrent projects and intake. Reservations, active work and blocked requests remain distinct.
Canceling records a cancellation. It never creates a successful outcome.Recovery controls depend on recorded ownership and runtime capability.

Appendix A / Current capability referenceExpand a category · all categories expand when printing

The working parts,
in plain English.

This list describes the current local implementation. Recorded demonstrations cover narrower scenarios; open release work is listed on the next page.

Projects and intake
  • Browse local folders and register Git projects; keep project settings, checks and execution histories separate.
  • Describe a task in Control Center; receive an answer, a focused clarification or department routing.
  • Preserve the original request, attached files and selected settings. New follow-ups from an opened conversation carry bounded prior context.
  • Read-only analysis can run without configured code tests. Implementation work requires acceptance checks; supported project test scripts can be discovered.
  • Default execution starts from the project’s committed version. Existing uncommitted edits remain in the user’s checkout.
People, departments and settings
  • Create and edit departments, heads and workers, with titles, capabilities and instructions.
  • Choose runtime, model and supported effort independently of the role; keep the actual run settings in history.
  • Use available specialists across projects automatically, with optional explicit project restrictions.
  • Move responsibility or replace a head through checked workspace updates; archive identities while preserving historical work.
  • Apply the five-department starter team and select bundled portraits. Portrait expressions are decorative.
Planning and controlled execution
  • Department heads propose bounded work with named owners. The coordinator validates the plan before dispatch.
  • Reserve the admitted workers, respect app-managed project/turn/writer capacity and show actual queue reasons.
  • Give workers separate candidate repositories and private temporary directories; preserve the original checkout.
  • Support planned dependencies, parallel workers, recorded peer messages and portable handoff records in the engine.
  • Keep the compatible direct command-line path for bounded work. Workspace requests use department planning and review.
Checks, review and delivery
  • Capture required check commands, results, logs and the exact candidate identity independently of worker claims.
  • Check the combined result again before accepting combined work; a passing individual worker result is insufficient.
  • Require a separate department-head review for workspace implementation results.
  • Keep “Reviewed analysis,” “Verified candidate,” “Answered,” “Failed” and “Canceled” meaningfully distinct.
  • Expose changed files, patches, recorded messages, review feedback, reports and unresolved issues through result details and engine artifacts.
  • Preserve local application, remote publication, merge and deployment as separate delivery decisions.
Issues and daily visibility
  • Create, inspect and edit issues with a preserved brief, priority, project, department and assigned owners.
  • Organize six lanes: Backlog, To Do, In Progress, In Review, Done and Canceled.
  • Start an issue explicitly through Control Center; ordinary board moves start no execution.
  • See all current project work, working and available agents, reservations and sign-in needs.
  • Use a compact persistent task feed, reopen saved conversations, inspect phase timings and expand detailed evidence.
  • Use project filters, responsive layouts, light/dark themes, keyboard-accessible controls and reduced-motion behavior.
  • Opt into browser notifications for completions or blockers where the browser supports them.
Connections and external plans
  • Discover configured Codex and Claude Code installations, versions and available model settings without starting paid work.
  • Use Connect to register and verify the local MCP bridge with supported coding clients.
  • Keep saved connector setup, a working tool connection and account readiness separate.
  • Use native sign-in controls through the detected executable; the provider handles the user’s authentication.
  • External coding agents can read projects/issues, create or update issues, submit a plan and explicitly start it.
  • Preserve full plan text and submission identity. Repeated identical submissions return the original record.
Recovery and lasting records
  • Store requests, task attempts, messages, settings, errors and result evidence locally.
  • Stop and explicitly resume supported runs, keeping saved configuration and previous work.
  • Use finite repairs and known temporary-error retries, with visible errors when the limit is reached.
  • Retry eligible failed work without erasing its history or treating uncertain worker ownership as permission to start another writer.
  • Restore queued work as held after a server restart; keep recorded stopped and failed outcomes truthful.
  • Inspect status and a live task view from the command line without taking over execution.
Local access and implementation boundaries
  • Open the local app through the macOS launcher, double-click command or root startup script.
  • Reuse the matching running workspace and its saved data; build the source checkout on a cold start.
  • Serve the browser interface on the local loopback address and check write-request origin and session identity.
  • Keep coordinator records outside the worker’s intended write area. New candidate copies have independent Git administration.
  • Separate source protection and configured write restrictions from full security isolation: read/test containment is not fully established.
  • Keep the application account-free for normal local use; installed coding providers still determine their own account and inference requirements.
Source snapshot: 14 September 2026, including local uncommitted implementation.Feature presence is different from complete release acceptance.
Appendix B / Evidence and release boundariesPrepared 14 September 2026

What the evidence supports.
What comes next.

The story is strongest when the working product and the planned product remain easy to tell apart.

Recorded demonstrations
  • September 13: a real external MCP client submitted a brief; Codex intake, head planning, one worker, independent tests and head review produced a checked local candidate.
  • September 14: a real source explanation completed with a report, unchanged-source evidence and department-head review.
  • September 14: two real read-only requests ran across separate departments and projects with recorded overlapping execution and passing head reviews.
  • Local launcher, connection setup and browser checks have separate records. They do not establish model execution by themselves.
Open product work
  • The Rust application, standalone installer, signed releases and tested updates are planned.
  • Independent installation and repeated everyday use by other developers remain release work.
  • Full Claude department-head workflow proof and the complete runtime containment suite remain open; the current supported paths have different evidence levels.
  • Full filesystem protection is not established. Separate repositories and write restrictions do not fully confine reads or test processes.
  • Dirty-work snapshots, automatic local candidate application, richer in-flight requirement changes, backup/restore UX and managed desktop background behavior are not complete current features.
  • One request at a time per project remains the workspace default. Automatic work spanning multiple departments from one brief is not established.
  • No customer adoption, broad performance advantage, general autonomy or full offline inference is claimed.
